## Release decision

The maintainer authorized preparation and formal publication of 0.1.0, with a
minimum Rust version of 1.88. The selected release channel is GitHub Releases
through `gh`. The previous manifest claimed 1.85, but the reachability path uses let
chains and fails to compile on 1.85. [Rust 1.88](https://blog.rust-lang.org/2025/06/26/Rust-1.88.0/)
stabilizes that syntax. Test
exactly 1.88.0 and current stable; no higher minimum or dependency update is
needed without new evidence.

This batch changes release metadata and documentation. Raising the declared
minimum also enables current Clippy's let-chain suggestions. Two nested
conditions in the Session waiter now use equivalent let chains, preserving
poll order, short-circuiting, and return values. Protocol behavior, public API,
dependency versions, and resource limits retain the implementation baseline.
The separate fuzz package remains unpublished and its path dependency tracks
the root package's exact version.

The release scope is stock `mosh-server` 1.4.0, IPv4, a fixed server endpoint,
external SSH bootstrap, and UTF-8 `xterm-256color` presentation. See
[compatibility](../compatibility.md) and [release notes](../../CHANGELOG.md).
LeanTTY's formal 1.6 acceptance is a separate product gate.

## Security and supply chain

The accepted [OCB3 exception](../decisions/0004-rustcrypto-ocb3-security-exception.md)
continues to apply: the primitive lacks an independent audit and complete
key-derived-state zeroization. The project has not added a cipher fallback or
claimed that a dependency advisory scan resolves this residual risk.

The source scan is a bounded pattern check, not proof against every possible
secret encoding. Registry versions and checksums match the previously reviewed
dependency graph, so its accepted unsafe boundaries continue to apply. The only
Rust diff is the reviewed waiter syntax; no cryptographic or secret-handling
code changed.

GitHub private vulnerability reporting was enabled and read back as enabled on
2026-09-05. [SECURITY.md](../../SECURITY.md) links to that private channel.

## Publication record

The clean candidate and annotated `v0.1.0` tag were pushed together in one
atomic Git push. GitHub Release `383241622` was then created and published
through `gh` as `wandcs`, with the inspected `.crate` and `SHA256SUMS` attached.
The returned asset digest equals the local package SHA-256 above. The remote
tag resolves to the exact release commit; it must not be moved. GitHub reports
`immutable = false`, so this policy is not enforced by server-side release
immutability.

The root manifest permits only crates.io if a registry upload is later chosen;
the fuzz package remains `publish = false`. The default WSL environment had no
configured registry token or user credential provider. The maintainer chose
publication through `gh`; no registry credential was printed, copied, or
installed, and `cargo publish` was not run without `--dry-run`.

Consumers can use the [README's Git dependency](../../README.md#status).
After publication, a fresh consumer resolved that remote tag to `aed5865c`
and compiled the public `Session` export with Rust 1.88.0. This used a fresh
consumer lockfile and passed `cargo +1.88.0 check`; the release package's own
lockfile and bytes were unchanged.
Post-release documentation records the completed publication on `main`; the
tag and attached package retain the verified candidate's original bytes.

LeanTTY currently pins the old Git revision with `version = "=0.0.0"`. Its
later upgrade must change both the full revision (or registry source) and the
version requirement to 0.1.0, then run its own affected acceptance gates.
